# ТЗ — лендинг «Код уважения» (курс №1)

Этот файл **дополняет**, а не заменяет пакет дизайна в `_extracted/` (`claude-code-brief.md`, `design-spec.md`, `content-reference.md`, `asset-manifest.md`, `brand-tokens.json`). Перед сборкой читать оба файла вместе — здесь добавлены поправки по композиции/анимации (по итогам разбора через модуль modern-design-2026) и вся техническая часть (бэкенд, оплата, хранение файла, безопасность), которых в оригинальном дизайн-пакете нет.

Проект состоит из трёх частей с общей архитектурой:
1. **Лендинг «Код уважения»** (этот файл) — оплата → выдача PDF-файла.
2. **Лендинг курса №2** (видео-модули) — оплата → выдача одноразовой ссылки-приглашения в закрытый Telegram-канал. ТЗ по нему — отдельным файлом, когда будет свой дизайн-пакет.
3. **Мини-страница с книгами** — статическая, без оплаты, ссылка-баннер с обоих лендингов.

Ботов нет и не будет — только эти три статические страницы с серверной логикой на бэкенде.

## 1. Поправки к дизайну (дополнение к `design-spec.md`)

Общий визуальный язык (палитра ink/paper/gold, шрифтовая тройка Cormorant Garamond + Lora + Manrope, чередование тёмных/светлых секций) — оставляем как есть, это сильная часть референса. Ниже — что поменять в **композиции**, не в стиле:

- **Ряды из 6 одинаковых иконок** («Коротко о навыках» и «Что вы получите») — не делать ровным рядом/сеткой одинаковых карточек. Собрать бенто-раскладкой: разные по размеру ячейки (например, 2 крупные + 4 обычные), не единообразно.
- **Блок «О чём этот курс / В курсе вы найдёте»** — сейчас плоский текст на белом. Добавить лёгкую карточность: тень, `paper-texture.svg` как фактура фона (сейчас в макете почти не считывается, хотя ассет подготовлен).
- **Анимация** — сдержанно, не перегружать:
  - Один плавный заход контента hero при загрузке (staggered reveal, ~600-800мс)
  - Лёгкий hover на кнопках и карточках (scale/тень, ~200мс)
  - Scroll-reveal для секций ниже экрана (fade-up при появлении во вьюпорте)
  - Уважать `prefers-reduced-motion` — эту анимацию отключать
  - Никаких зацикленных анимаций, всплывающих окон, таймеров — этого не было в референсе и не нужно добавлять

## 2. Поправки к тексту (дополнение к `content-reference.md`)

Три списка («Коротко о навыках» / «В курсе вы найдёте» / «Что вы получите») сейчас пересекаются по смыслу почти дословно. Развести по разным ролям:
- **Навыки** — что конкретно научитесь делать (поведенческий результат)
- **Содержание курса** — что физически внутри материала (структура, инструменты)
- **Результат** — что изменится в жизни (эмоциональный/социальный итог)

Убрать повторы одних и тех же формулировок («уверенность», «здоровые отношения», «границы») между этими тремя блоками.

Добавить рядом с именем автора строку доверия/авторитета (стаж, число клиентов, публикации — **точные цифры взять у заказчика, не придумывать**).

## 3. Техническая архитектура

### Хостинг
**Timeweb Cloud App Platform** — Node.js/Express-сервер, деплой по `git push`. Домен: `kod.privatebotrus.ru` (поддомен, независимый деплой от второго лендинга).

### База данных
**Timeweb Cloud DBaaS (PostgreSQL)** — доступ через `pg` (node-postgres), сырые параметризованные запросы. Без Supabase/ORM — см. `[[глобальная память RU-хостинг]]`.

Таблица `payments` (по аналогии со схемой вебинарного проекта, `supabase/schema.sql`):
```sql
create table payments (
  id uuid primary key default gen_random_uuid(),
  created_at timestamptz not null default now(),
  order_id text not null unique,
  email text,
  amount numeric(10,2) not null,
  status text not null default 'pending' check (status in ('pending','paid','failed')),
  robokassa_payload jsonb,
  paid_at timestamptz,
  access_token text,
  access_source text not null default 'auto' check (access_source in ('auto','manual')),
  granted_by text,
  notes text
);
create unique index on payments (access_token) where access_token is not null;
```

### Хранение и выдача PDF
- Файл лежит в **Timeweb S3** (приватный бакет, не публичный).
- После подтверждения оплаты (см. ниже) генерируется `access_token`, как на вебинаре.
- По валидному токену бэкенд генерирует **временную подписанную ссылку (presigned URL)** на скачивание, срок жизни ~10-15 минут — не постоянная публичная ссылка на файл.
- Токен в базе бессрочный ("доступ навсегда" из копирайта) — человек может зайти повторно в любой момент и получить свежую ссылку.

### Оплата — Robokassa
- Магазин: существующий **«Privatebot»** — Result URL переключаем на новый бэкенд **в момент запуска** обоих новых лендингов разом (не раньше, чтобы не задеть то, что там сейчас работает).
- Схема сигнатур и вебхука — переиспользуем 1:1 логику из `netlify/functions/_lib/robokassa.js` проекта вебинара (создание платежа, проверка Result URL подписи, идемпотентность повторных уведомлений).
- **Доступ выдаётся только через серверный Result URL**, никогда по браузерному Success URL — тот же принцип, что на вебинаре, после инцидента с зависшими платежами.
- Учитывать нюанс задержки подтверждения (по опыту вебинара — до 10 минут) — страница ожидания на клиенте должна ждать разумное время и не молчать при задержке (см. `payment-success.html` вебинара как образец).

### Секреты и `.env`
Согласно `AGENT_SECURITY_RULES_merged.md`/`AGENTS.md`, уже лежащим в этой папке: пароли Robokassa, ключи S3 и Postgres — только через переменные окружения Timeweb App Platform, `.gitignore` для `.env` до первого коммита, нигде не хардкодить и не выводить в чат/лог.

## 4. Безопасность — обязательные пункты для этого проекта конкретно

- Приватный S3-бакет — файл недоступен по прямой ссылке без подписи.
- Presigned URL с ограниченным временем жизни (10-15 мин), не бессрочная ссылка.
- Rate limiting на публичные эндпоинты (`create-payment`, `check-payment`, генерация ссылки на скачивание) — защита от перебора токенов/спама заказов.
- Параметризованные SQL-запросы через `pg`, без конкатенации строк.
- Проверка статуса оплаты — только на сервере (в момент выдачи ссылки на PDF), никогда не доверять параметрам из браузера.
- Общие сообщения об ошибках наружу, детали — только в серверный лог.
- Двойной проход после написания кода оплаты/выдачи файла: сначала пишем, затем отдельным шагом явно проверяем по OWASP Top 10.

## 5. Админ-панель

Забыли учесть раньше — нужна, по образцу админки вебинарного проекта. Переиспользуем ту же архитектуру 1:1 (`admin-*` функции + страница `/admin/` вебинара — как эталон), не изобретаем заново:

- **Авторизация**: один общий пароль на админку (не сотрудники по отдельности) — хеш через bcrypt, хранится в таблице `admin_credentials` в базе (не в `.env`), чтобы заказчик мог сам сменить пароль из интерфейса. Смена пароля требует ввода текущего — угнанная сессия не даёт заблокировать настоящего админа.
- **Таблица заказов**: список платежей (дата, email, сумма, статус, источник auto/manual) — та же логика, что в вебинарной админке.
- **Ручная выдача доступа**: кнопка создать запись `access_source = 'manual'` с новым `access_token` — на случай, если Робокасса подтвердила с опозданием или что-то пошло не так, как уже не раз бывало на вебинаре.
- **Кнопка «Скопировать ссылку»** рядом с каждой оплаченной записью — копирует `https://kod.privatebotrus.ru/?access=<token>`, чтобы можно было вручную переслать клиенту. Учитывая находку на вебинаре (заказчик иногда создаёт ручную запись, но забывает реально отправить ссылку) — явно проговорить это заказчику при передаче: сама запись в базе доступ не открывает, пока ссылку не отправили человеку.
- **Rate limiting** на форму логина админки (защита от подбора пароля) — тот же принцип, что в общих правилах безопасности.
- Стилистика — в духе брендинга лендинга (ink/paper/gold), не дефолтная админ-панель — как было сделано и оценено на вебинаре.

Пока делаем отдельную админку именно под этот лендинг, без объединения со вторым. Идея общей панели на оба продукта — на потом, после того как этот лендинг будет готов и обкатан; не усложняем сборку сейчас.

## 6. SEO и оптимизация загрузки (обязательно перед сдачей)

Отдельно зафиксировано как обязательный пункт, не опция:

- **Базовое SEO**: `<title>`, `meta description`, Open Graph (`og:title`, `og:description`, `og:image`, `og:url`, `og:type`) и `twitter:card` — по той же схеме, что уже сделана на вебинарном лендинге. `robots.txt`, `sitemap.xml`, семантическая разметка (один `h1`, логичная иерархия заголовков — уже заложена в вёрстку).
- **Оптимизация загрузки**:
  - Hero-изображения (SVG с встроенным фото+шрифтом) сейчас весят 2-3.3 МБ каждое — это уже проверено и сжать без потери качества нельзя (85%+ веса — уже сжатый JPEG внутри SVG, дальше только через потерю качества). Минимум — `loading="eager"` только для hero (он и так первый экран), `loading="lazy"` для всех остальных изображений на странице (формат/результаты/CTA секции).
  - Остальные растровые изображения (`format-mountains`, `results-mountains`, `cta-mountains`) — использовать уже подготовленные WebP-версии с PNG-фолбэком (сделано), не грузить лишний вес.
  - Google Fonts подключены сейчас через `<link>` на сторонний домен — рассмотреть локальный self-host шрифтов (`woff2`) на этапе финальной сборки, чтобы не тянуть лишний внешний DNS/TLS round-trip.
  - Минифицировать `style.css`/`main.js` перед деплоем в прод (не обязательно на каждый локальный тест, но перед сдачей — да).
