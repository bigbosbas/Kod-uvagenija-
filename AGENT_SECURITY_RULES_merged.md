# AGENT_SECURITY_RULES.md
## Прямые указания для AI-агента (Claude, Cursor, и др.) при разработке кода

> Разместите этот файл в корне проекта (например, как `CLAUDE.md` или `.cursorrules`). Агент должен соблюдать эти правила автоматически, без напоминаний.
>
> Эта версия объединяет исходный AGENT_SECURITY_RULES.md с содержимым слайдов 11–12 презентации «Безопасность при вайб-кодинге». Шаблон Claude.md со слайда 11 (секреты / БД / аутентификация / зависимости / фронтенд) полностью совпадает по содержанию с разделами ниже, поэтому не продублирован — весь его смысл уже покрыт правилами из исходного файла. Из чек-листа со слайда 12 в раздел 4 добавлены только пункты, которых не было ни в одном из разделов ниже.

---

## 🔴 ЗАПРЕЩЕНО (Never)

### Секреты и ключи
- НИКОГДА не хардкодить API-ключи, пароли, токены, секреты напрямую в код.
- НИКОГДА не выводить реальные значения секретов в чат, лог, комментарии или примеры кода.
- НИКОГДА не коммитить `.env` и файлы с секретами в git.
- НИКОГДА не размещать секреты или ключи в клиентском JavaScript (всё, что уходит в браузер, — публично).

### Аутентификация и авторизация
- НИКОГДА не размещать проверку прав доступа (ролей, подписок, тарифов) только на фронтенде/в JavaScript.
- НИКОГДА не писать условие проверки прав без явной блокировки по умолчанию (запрет должен быть default, а не исключение).
- НИКОГДА не пропускать проверку авторизации для операций удаления/изменения/чтения чужих данных.

### База данных
- НИКОГДА не строить SQL-запросы через конкатенацию строк или f-string с пользовательским вводом.
- НИКОГДА не возвращать в HTTP-ответе детали ошибок БД (stack trace, структуру таблиц, тексты SQL-исключений).
- НИКОГДА не оставлять Row Level Security (RLS) отключённым в Supabase/Postgres при наличии клиентского доступа.

### Фронтенд
- НИКОГДА не вставлять пользовательский ввод через `innerHTML` — только `textContent` или санитайзер.
- НИКОГДА не использовать `eval()` или `Function()` с любыми внешними/пользовательскими данными.

### Зависимости
- НИКОГДА не устанавливать пакет, название которого не проверено (риск slopsquatting — AI может «придумать» несуществующее имя пакета).
- НИКОГДА не добавлять зависимость без явного указания точной версии (в `requirements.txt` / `package.json`).

### Файлы и загрузки
- НИКОГДА не создавать функцию загрузки файлов без проверки типа, размера и защиты от path traversal.
- НИКОГДА не делать публично доступным bucket/storage с пользовательскими документами (паспорта, фото, персональные данные) без явного запроса и понимания последствий.

## 🟢 ОБЯЗАТЕЛЬНО (Always)

### Секреты и ключи
- Всегда читать секреты из переменных окружения (`.env` + `python-dotenv` / `process.env`).
- Всегда добавлять `.env`, `*.env`, `.env.local` в `.gitignore` — до первого коммита, автоматически, без запроса.
- Если пользователь просит вставить ключ в промпт — предложи вместо этого использовать placeholder `YOUR_API_KEY_HERE` и вставить ключ вручную в `.env`.

### Аутентификация
- Всегда проверять права доступа на сервере, независимо от того, что проверено на клиенте.
- Всегда хешировать пароли через bcrypt или argon2 — никогда plain text или простой хеш (MD5/SHA1).
- Всегда реализовывать rate limiting для публичных эндпоинтов и форм авторизации.

### База данных
- Всегда использовать параметризованные запросы / ORM с автоматическим экранированием.
- Всегда возвращать пользователю общее сообщение об ошибке, детали — только в серверный лог.

### Зависимости
- Всегда проверять существование и репутацию пакета (дата создания, число загрузок, автор) перед установкой, если пакет предложен агентом впервые.
- Всегда запускать `npm audit` / `pip audit` после установки новых зависимостей и сообщать о найденных уязвимостях.

### Общий процесс
- После генерации любой функции, связанной с доступом к данным, оплатой, аутентификацией или загрузкой файлов — автоматически выполнять самопроверку по OWASP Top 10 и сообщать о найденных и исправленных проблемах.
- При написании кода для новой фичи по умолчанию использовать «безопасную» версию реализации, даже если пользователь не указал слово «безопасный» в промпте.
- Явно предупреждать пользователя, если запрошенная функциональность (например, «сделай данные видимыми всем») создаёт риск утечки персональных данных.

## 🟡 ПОВЕДЕНЧЕСКИЕ ПРАВИЛА АГЕНТА

- Если пользователь вставил реальный API-ключ или пароль в чат — предупредить, что это небезопасно, и рекомендовать немедленно ротировать (заменить) ключ.
- Если запрошенная фича логически требует serverside-проверки, но пользователь просит "просто быстро сделать" — реализовать безопасный вариант по умолчанию, а не наиболее быстрый.
- При генерации кода с известными паттернами риска (SQL-инъекция, XSS, открытая авторизация, публичные bucket) — не создавать такой код даже "как пример", если не указано явно, что это учебный/демонстрационный контекст.
- Никогда не заявлять, что код "полностью безопасен" без реального аудита — вместо этого указывать, какие проверки были выполнены.
- **[новое, слайд 12]** Новый код, сгенерированный AI, читать как код незнакомого стажёра — не доверять по умолчанию тому, что он «наверняка учёл» последствия для безопасности.

## ✅ ЧЕК-ЛИСТ ПЕРЕД КОММИТОМ/ДЕПЛОЕМ (новое, слайд 12)

Пункты этого раздела — не новые правила, а короткая проверка перед коммитом, что правила выше реально соблюдены на практике:

1. Ни один реальный ключ или пароль не был написан прямо в переписке с AI-агентом (даже как пример) — только через `.env`.
2. Использован двойной проход: код сначала сгенерирован, затем отдельным запросом явно проверен на OWASP Top 10, а не только автоматической фоновой самопроверкой агента.
3. Этот файл (объединённые security-правила) действительно лежит в корне проекта как `CLAUDE.md` / `.cursorrules`, а не просто существует где-то отдельно.
4. Новый код прочитан целиком человеком, а не принят «на веру» от агента (см. поведенческое правило выше).

Остальные пункты исходного чек-листа со слайда 12 (ключи в `.env`, `.gitignore` до первого commit, пакеты проверены на npmjs/pypi, SQL-запросы параметризованные, аутентификация на сервере, `npm audit`/`pip audit` запущен) — это те же правила из разделов «Запрещено» и «Обязательно» выше, отдельно не повторяются.

## Краткая сводка (для быстрой проверки перед коммитом)

| Категория | Правило |
|---|---|
| Ключи | Только в `.env`, никогда в коде и в чате |
| Git | `.gitignore` настроен до первого commit |
| Авторизация | Проверка прав — только на сервере |
| SQL | Только параметризованные запросы |
| Пароли | bcrypt / argon2 |
| Фронтенд | `textContent`, не `innerHTML`; без `eval()` |
| Пакеты | Проверены на npmjs/pypi, версии зафиксированы |
| Загрузка файлов | Проверка типа, размера, path traversal |
| Аудит | `npm audit` / `pip audit` после установки зависимостей |
| Самопроверка | OWASP Top 10 после каждой чувствительной функции |
| Двойной проход | Генерация → отдельный явный запрос на аудит |
| Чтение кода | Как код незнакомого стажёра, не «на веру» |
